## 4. 案例紀實

### 案例 1：#42 通知渠道設計先行策略驗證（04-20）

- **背景**：Epic E 核心 #41 於 4/19 完成合併後，#42 依賴鏈解除。直接實作需動到 `alert_engine.py` 核心路徑 + 新增 3 個 Notifier + 1 個 Manager（估 10h），超出「每次 1 PR / ≤ 50 行」紀律。
- **執行**：wLab:director 決策改採「設計文件先行」，wEng:backend-dev 主責撰寫 `docs/design/notification-channels.md`，涵蓋架構圖 / 介面定義（`BaseNotifier` + `NotificationPayload` / `NotificationResult` dataclass）/ 3 個 Notifier 草案 / YAML 設定 Schema / 訊息模板 / 測試策略 / 安全合規。
- **成果**：產出 ~300 行設計文件，切分為 2 個實作 PR（PR A：Base + Email / PR B：Webhook + LINE + Manager），每個 ≤ 300 行、4h 可完成。
- **學習**：設計先行策略連續三輪（#41 階段 / #42 / #96 階段二）驗證有效，零返工；建議後續 10h 以上任務均採此模式。

### 案例 2：#96 階段二服務層設計 — 使用者核心需求響應（04-20）

- **背景**：使用者於每日工作流多次強調「**AI 輔助派工 + 結構化紀錄 + 正式美觀報告**」為最高優先。階段一文件層於 4/19 完成後，需要將派工流程從 Markdown 手動維護升級為 API + SQLite 驅動。
- **執行**：wLab:director 主責，wEng:backend-dev 協同介面規劃，產出 `docs/design/director-allocation-service.md` ~530 行，包含：
  - **5 個 Pydantic 模型**：`Allocation` / `DailyAllocationSheet` / `WorkRecord` / `AiAdvice` / `TeamLoadSnapshot`
  - **3 張 SQLite 表**：`allocations` / `daily_sheets` / `work_records`（含 3 個 index）
  - **規則式 AI 輔助演算法**：任務分類 → 負載查詢 → 優先序計分 → 工時估算 + 替代方案
  - **11 個 REST API 端點**：CRUD / 派工建議 / 負載快照 / 工作紀錄 / Markdown 匯入
  - **Markdown ↔ DB 雙向同步**：`AllocationMarkdownConverter`
  - **6 個實作 PR 切分**：models → engine → converter → API → records → docs（14 h）
- **成果**：設計契約完整固化，階段二實作預計 04-26 啟動，5/01 完工。
- **學習**：使用者核心需求首次從文字敘述轉為可實作契約；模型 / API / 演算法三維度齊備後，後續 PR 可精準落地，降低反覆修改風險。

### 案例 3：派工系統模板第四次實戰 — 空窗恢復日（04-23）

- **背景**：4/21-4/22 連續兩日空窗後，4/23 為本週首個恢復工作日。派工系統於 4/19 首次實戰、4/20 三輪連續實戰後，本輪為「非連續日」情境的壓力測試。
- **執行**：本日派工單首次納入 3 項任務（例行掃描 / 首份週報 / 排程重整），並於第 1 節「本日決策摘要」首度誠實揭露排程滑移（非粉飾）。
- **成果**：模板於「空窗恢復日」情境仍結構穩定；首度啟用「正式報告模板」（本週報即實例），驗證 `tmpl-formal-report.md` 7 章節 + 3 附錄結構對週報適用。
- **學習**：(1) 排程滑移透明化有助於使用者信任；(2) 報告模板需搭配 4 週以上素材才能充分驗證；(3) 派工 → 紀錄 → 報告三層鏈結可作為後續自動化的完整樣本。
