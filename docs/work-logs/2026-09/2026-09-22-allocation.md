## 4. AI 輔助派工建議

### 瓶頸

- **CI 是唯一瓶頸**。5 項缺陷修復、4 個測試修復、6 個 Issue 關閉，全都應該在 CI 能給回饋的前提下進行。先復綠，其餘才有意義。
- `wEng:` 單一團隊承接 P0 全部工作，其他四個團隊閒置。但這是正確的序列化——並行開新功能只會擴大未驗證程式碼面積。

### 風險

- **最高風險是「文件說完成、實際有缺陷」的認知落差**。#96 的「雙向無損同步」在文件、日報、roadmap 三處都標 ✅ 完成，實際每次往返丟 4 個欄位。若不修就往上疊 Epic A 的案例學習（同樣依賴 Markdown ↔ DB），會把有損基礎變成隱性資料遺失來源。
- CI 的 ruff/black 未 pin 版本（`pip install ruff black mypy`），與 `requirements.txt` 的 `ruff==0.6.0` 不一致。ruff 升版會無預警帶進新規則（本次實測為 0.15.8，`TCH` 已更名 `TC`、`UP042` 為新規則）。

### 資源建議

- P0 兩項（復綠 + 測試）可同一個 session 完成，約 4h。
- P1 三項可並行分派。
- 功能面（Phase 15 多風場 / Epic A 案例學習）建議等 CI 綠燈後再定向。

### 排程建議

```
復工週    P0 復綠 + 修測試        → 主幹恢復回饋能力
          P1 CI 防護 + Issue 對齊 → 避免再次腐化

```
