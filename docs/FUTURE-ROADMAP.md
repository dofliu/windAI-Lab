# WindAI Lab — 未來發展規劃

> 建立日期：2026-04-04 | 最後更新：2026-04-04
> 目前進度：Phase 10 完成（92%）
> **核心願景：打造一間真實的風場運維服務公司**

---

## 1. 願景定位

### 我們要做什麼

WindAI Lab 不只是研究工具，而是一間**真實的風場運維 AI 服務公司**：
- 具備完整的**運維團隊**（AI 代理），能協助各種風場問題
- 能接入**真實風場資料**，持續監控、自動診斷、主動服務
- 具備完整的**服務閉環**：偵測 → 告警 → 診斷 → 工單 → 執行 → 結案 → 學習

### 現在在哪裡 vs 要去哪裡

```
現在（研究平台）                       目標（運維服務公司）
─────────────────                     ─────────────────
丟檔案 → 分析 → 看結果                持續監控 → 自動偵測 → 即時告警
記憶體 → 重啟全消失                    資料庫 → 歷史可追溯 → 案例可學習
分析出結果就結束了                      分析 → 工單 → 派工 → 結案 → 學習
單一風場離線分析                        多風場即時監控 + 遠端服務
```

---

## 2. 三大缺口分析

| 缺口 | 現狀 | 目標 | 影響 |
|------|------|------|------|
| **即時性** | 靜態檔案分析 | 即時 SCADA 串流 + 自動告警 | 無法服務真實風場 |
| **持久性** | 記憶體儲存 | 資料庫 + 歷史回溯 + 案例學習 | 無法累積經驗 |
| **服務閉環** | 分析即結束 | 告警→工單→派工→結案→學習 | 無法提供完整服務 |

---

## 3. 演進路線圖

### Step 1：打地基 — 持久化 + 服務閉環（Phase 11-13）

> **關鍵字**：讓系統「記得住」、「能追蹤」、「會通知」

#### Phase 11 — 前端戰情中心 + 分析面板

| 項目 | 說明 | 狀態 |
|------|------|------|
| MissionView 戰情中心 | 任務進行時自動切換 UI，只顯示參與代理與進度條 | ⬜ |
| AnalysisDashboard 分析面板 | 右側即時圖表（功率曲線、殘差圖、健康趨勢） | ⬜ |
| ViewSwitcher 自動切換 | 偵測任務狀態，office ↔ mission 自動切換 | ⬜ |
| 技能管線進度條 | 每個 skill 獨立進度（loading → running → done） | ⬜ |

#### Phase 12 — 持久化儲存

| 項目 | 說明 | 狀態 |
|------|------|------|
| SQLite/PostgreSQL 資料庫 | 任務記錄、代理工作日誌、分析結果持久化 | ⬜ |
| 歷史查詢 API | `GET /api/tasks/history` 分頁查詢 | ⬜ |
| 前端歷史面板 | 可回溯過去的任務結果與報告 | ⬜ |
| 分析結果快照 | 每次分析的完整輸入/輸出/參數存檔 | ⬜ |

#### Phase 13 — 告警系統 + 工單管理

| 項目 | 說明 | 狀態 |
|------|------|------|
| 告警規則引擎 | 可配置閾值規則（健康分數 < 0.7 → 告警） | ⬜ |
| 通知渠道 | Email / Webhook / LINE Notify 告警推播 | ⬜ |
| 工單系統 (Work Order) | 診斷結果 → 自動產生工單 → 狀態追蹤 | ⬜ |
| 工單生命週期 | 待處理 → 已指派 → 進行中 → 完成 → 結案 | ⬜ |
| 工單儀表板 | 前端 Kanban 面板，拖拉式狀態變更 | ⬜ |

**Phase 11-13 完成後的系統能力**：
```
使用者丟入 SCADA 檔案
  → 代理自動分析
  → 結果存入資料庫（不再消失）
  → 異常觸發告警（通知運維人員）
  → 自動產生工單（追蹤處理進度）
  → 歷史可查詢（案例可回溯）
```

---

### Step 2：接真實風場 — 即時串接 + 多風場管理（Phase 14-16）

> **關鍵字**：讓系統「看得到」真實風場、「管得了」多個客戶

#### Phase 14 — 即時資料連接器

| 項目 | 說明 | 狀態 |
|------|------|------|
| Data Connector 抽象層 | 統一的資料來源介面（檔案 / API / OPC UA / MQTT） | ⬜ |
| REST API 連接器 | 定時拉取風場 REST API 的 SCADA 資料 | ⬜ |
| OPC UA 連接器 | 直接接收風場 PLC 的即時資料 | ⬜ |
| 串流處理管線 | 每 10 分鐘自動拉取 → 清洗 → 分析 → 告警判斷 | ⬜ |
| 連線健康監控 | 資料來源斷線偵測 + 自動重連 + 告警 | ⬜ |

#### Phase 15 — 多風場管理

| 項目 | 說明 | 狀態 |
|------|------|------|
| 風場 (WindFarm) 資料模型 | 風場 → 風機群組 → 單機，階層式管理 | ⬜ |
| 風場儀表板 | 每個風場獨立的總覽頁（可利用率、容量因子、告警數） | ⬜ |
| 跨風機比較 | 同風場內多台風機的健康狀態/效能並列比較 | ⬜ |
| 風場級 KPI | 整場可利用率、發電量、尾流損失統計 | ⬜ |
| 客戶管理 | 客戶 → 合約 → 風場的對應關係 | ⬜ |

#### Phase 16 — 歷史案例學習

| 項目 | 說明 | 狀態 |
|------|------|------|
| 案例自動記錄 | 每次故障診斷 → 解決方案 → 寫入 RAG 知識庫 | ⬜ |
| 相似案例推薦 | 新故障 → 語意搜尋歷史案例 → 推薦解決方案 | ⬜ |
| 故障模式知識圖譜 | 故障類型 → 根因 → 症狀 → 解決方案的關聯圖 | ⬜ |
| 維護效果追蹤 | 維修後效能是否恢復？追蹤維修前後對比 | ⬜ |

**Phase 14-16 完成後的系統能力**：
```
真實風場 SCADA → 即時串流進入系統
  → 多風場同時監控
  → 自動異常偵測 → 告警 → 工單
  → 歷史案例自動推薦解決方案
  → 客戶可看到自己風場的即時狀態
```

### Step 3：完整運維服務 — 派工 + 備品 + 報告自動化（Phase 17-19）

> **關鍵字**：讓系統能「派人去做」、「知道需要什麼零件」、「自動向客戶報告」

#### Phase 17 — 派工與排程系統

| 項目 | 說明 | 狀態 |
|------|------|------|
| 技術員管理 | 技術員清單、技能標籤、可用時段 | ⬜ |
| 自動派工 | 工單 → 根據技能/距離/排程自動推薦技術員 | ⬜ |
| 行動端界面 | 技術員手機查看工單、回報進度、上傳照片 | ⬜ |
| 維護排程最佳化 | 考慮天氣窗口、備品到貨、人力安排的最佳化排程 | ⬜ |

#### Phase 18 — 備品庫存管理

| 項目 | 說明 | 狀態 |
|------|------|------|
| 備品資料庫 | 零件清單 → 適用風機型號 → 庫存數量 → 存放位置 | ⬜ |
| 故障→備品關聯 | 故障類型自動推薦需要的零件清單 | ⬜ |
| 庫存預警 | 庫存低於安全水位 → 自動通知採購 | ⬜ |
| 採購建議 | 根據歷史故障頻率預測未來備品需求 | ⬜ |

#### Phase 19 — 自動報告 + SLA 追蹤

| 項目 | 說明 | 狀態 |
|------|------|------|
| 自動報告排程 | 週報/月報自動產生 → 寄送客戶 | ⬜ |
| SLA 追蹤 | 回應時間、解決時間、可利用率保證 | ⬜ |
| 客戶入口 | 客戶登入查看自己風場的狀態、報告、工單 | ⬜ |
| 績效儀表板 | 運維團隊的 KPI（回應時間、結案率、客戶滿意度） | ⬜ |
