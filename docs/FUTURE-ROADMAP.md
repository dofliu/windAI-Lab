# WindAI Lab — 未來發展規劃

> 建立日期：2026-04-04 | 目前進度：Phase 10 完成（92%）

本文件整理 WindAI Lab 的未來發展方向，分為短期（Phase 11-12）、中期、長期三個階段，供團隊討論與決策。

---

## 1. 現況瓶頸分析

在規劃未來之前，先盤點目前系統的主要瓶頸與不足：

| 瓶頸 | 影響 | 嚴重度 |
|------|------|--------|
| **前端缺乏戰情中心** | 任務執行時 UI 體驗不佳，無法聚焦正在工作的代理 | 高 |
| **分析結果無即時圖表** | 診斷完成後只有文字報告，缺乏視覺化互動 | 高 |
| **無持久化儲存** | 重啟後任務記錄與工作日誌消失 | 中 |
| **模型種類有限** | 只有 KNN-NBM、XGBoost、線性退化，缺深度學習模型的實戰部署 | 中 |
| **單機部署** | 無法處理大型風場（100+ 風機）的即時分析需求 | 低（研究用足夠） |
| **缺乏使用者認證** | 適合個人/實驗室使用，不適合多團隊 | 低 |

---

## 2. 短期規劃：Phase 11-12（補齊核心體驗）

### Phase 11 — 前端戰情中心 + 分析面板

**目標**：讓「執行任務」的體驗從「看文字 log」升級為「即時視覺化監控」。

| 項目 | 說明 | 預估工時 |
|------|------|----------|
| **MissionView 戰情中心** | 任務進行時自動切換 UI，只顯示參與中的代理與進度條 | 4h |
| **AnalysisDashboard 分析面板** | 右側面板顯示即時圖表（功率曲線、殘差圖、健康趨勢） | 4-6h |
| **ViewSwitcher 自動切換** | 偵測任務狀態，自動在 office ↔ mission 模式間切換 | 1-2h |
| **技能管線進度條** | 每個 skill 顯示獨立進度（loading → running → done） | 2h |

**預期成果**：使用者下指令後，UI 自動進入戰情模式，即時顯示每個技能的執行進度與圖表。

### Phase 12 — 持久化 + 歷史回溯

**目標**：任務結果不再因重啟而消失。

| 項目 | 說明 | 預估工時 |
|------|------|----------|
| **SQLite 任務記錄** | 記錄每次指令的輸入、管線、結果、耗時 | 3-4h |
| **工作日誌持久化** | 代理的 work_log 寫入資料庫 | 2h |
| **歷史查詢 API** | `GET /api/tasks/history` 分頁查詢 | 2h |
| **前端歷史面板** | 可回溯過去的任務結果與報告 | 3h |

## 3. 中期規劃：研究能力深化

### 3.1 深度學習模型實戰部署

目前 LSTM 與 Weibull 模型已實作但尚未整合到管線中。

| 項目 | 說明 | 價值 |
|------|------|------|
| **LSTM 功率預測管線** | 訓練→驗證→部署為技能模組 | 對比 KNN-NBM 的預測精度 |
| **Transformer 時序預測** | 引入 PatchTST / iTransformer | 學術前沿方法論 |
| **GNN 風場拓撲建模** | Graph Neural Network 學習風機間空間關係 | 尾流效應的資料驅動建模 |
| **遷移學習** | 在大型風場預訓練，小型風場微調 | 解決小資料量場景 |

### 3.2 多風場比較分析

| 項目 | 說明 |
|------|------|
| **跨風機儀表板** | 同時顯示多台風機的健康狀態比較 |
| **風場級效能 KPI** | 可利用率、容量因子、尾流損失的風場級統計 |
| **基準線比較** | 同型號風機在不同風場的效能對比 |

### 3.3 RAG 知識庫強化

| 項目 | 說明 |
|------|------|
| **PDF 全文解析** | 支援論文 PDF 直接匯入（表格、圖片、公式） |
| **引用追蹤** | 自動追蹤論文間的引用關係 |
| **知識圖譜** | 建構風力發電領域的概念關係圖 |
| **多語言支援** | 支援英文+中文論文的跨語言檢索 |

### 3.4 Claude Code 代理強化

| 項目 | 說明 |
|------|------|
| **更多 slash commands** | 完善 `/data:validate`, `/domain:standard` 等指令 |
| **代理間自主協作** | Leadership 代理根據任務自動組建團隊 |
| **學習記憶** | 代理記住使用者偏好與歷史分析模式 |

## 4. 長期願景：產學整合平台

### 4.1 即時資料串接

| 項目 | 說明 |
|------|------|
| **OPC UA 串接** | 直接接收風場 PLC 的即時 SCADA 資料 |
| **串流處理** | Kafka/Redis Stream 處理即時資料流 |
| **即時告警** | 異常偵測 → 自動觸發告警通知 |

### 4.2 部署與擴展

| 項目 | 說明 |
|------|------|
| **Kubernetes 部署** | 支援多節點橫向擴展 |
| **GPU 推論服務** | 深度學習模型的 GPU 加速推論 |
| **使用者認證** | OAuth2 / SSO 多團隊權限管理 |
| **多租戶** | 不同風場/團隊的資料隔離 |

### 4.3 學術輸出

| 項目 | 說明 |
|------|------|
| **開源社群** | 發布為開源專案，吸引研究者貢獻 |
| **論文發表** | 以平台架構或分析方法發表期刊論文 |
| **教學套件** | 為風能課程提供互動式教學環境 |
| **基準測試集** | 建立標準化的風機故障診斷 benchmark |

## 5. 建議的執行順序

基於**使用者價值**與**技術可行性**排序：

```
短期（1-2 週）
├── Phase 11：戰情中心 + 分析面板 ← 最大 UX 提升
└── Phase 12：SQLite 持久化 ← 解決資料遺失痛點

中期（1-3 個月）
├── LSTM/Transformer 模型管線 ← 學術價值高
├── 多風場比較分析 ← 實用價值高
├── RAG PDF 全文解析 ← 研究生最需要
└── 更多 slash commands ← 易於實作

長期（3-6 個月+）
├── OPC UA 即時串接 ← 需要實際風場合作
├── Kubernetes 部署 ← 需要基礎設施
└── 開源+論文發表 ← 需要文件完善
```

## 6. 待討論議題

以下是需要團隊討論決定方向的開放性問題：

### 議題 A：模型策略

> 目前以傳統 ML（KNN, XGBoost）為主，LSTM 已實作但未整合。
> 是否優先推進深度學習管線？還是先強化現有模型的功能完整度？

**選項**：
1. **深度優先**：完善 LSTM → 加入 Transformer → GNN，追求學術前沿
2. **廣度優先**：先補齊多風場比較、跨風機分析等功能性需求
3. **混合策略**：Phase 11-12 補 UI/UX，同時平行開發一個新模型

### 議題 B：部署目標

> 目前是單機 Docker Compose，適合個人/實驗室使用。
> 是否需要支援多人同時使用？是否需要接真實風場資料？

**選項**：
1. **研究導向**：維持單機，專注模型與分析能力
2. **應用導向**：加入認證、持久化、即時串接，往產品化方向走
3. **教學導向**：優先教學套件、互動式教學環境

### 議題 C：開源策略

> 系統架構已具備開源價值（技能拆分 + 聘用制 + 可插拔 Renderer）。
> 何時開源？需要準備什麼？

**需要準備**：
- [ ] 完善 README 與快速入門指南
- [ ] 移除內部資料與敏感設定
- [ ] 建立 Contributing Guide
- [ ] 設計 Plugin API（讓社群貢獻新技能/Renderer）
- [ ] 選擇授權條款（MIT / Apache 2.0 / GPL）

### 議題 D：研究發表

> 哪些成果適合發表論文？目標期刊為何？

**可能的論文方向**：
1. **系統論文**：多代理協作的風力發電 AI 研究平台（目標：Renewable Energy / SoftwareX）
2. **方法論文**：技能拆分 + YAML 驅動的 AutoML 管線設計（目標：Engineering Applications of AI）
3. **應用論文**：基於 SCADA 的風機故障診斷比較研究（目標：Wind Energy）
